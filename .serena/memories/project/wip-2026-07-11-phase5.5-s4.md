## Pin look (globe/Pins.ts — full rework)
- THREE instanced draws around ONE angular-constant head radius `size` (clamp 6..45,000 m): STEM
  (unit open cylinder, vertex-alpha `stemTopAlpha·y²` fade to base, DoubleSide) · HEAD (sphere
  16×12, ShaderMaterial: core `headCoreAlpha` × shimmer + a fresnel rim; the raycast pick target) ·
  FLARE (additive billboard quad, alpha gated by `smoothstep(flareThreshold 0.86, 1, shimmer)`, so
  flares appear ONLY at twinkle peaks).
- Shared per-instance attributes `aColor`/`aSeed` as our own InstancedBufferAttributes (no reliance
  on three's instanceColor define dance), and ONE `uTime` uniform object shared by head and flare so
  their shimmer stays in sync.
- Stem height = size × (3.6 + 2.8·stagger01) clamped [30, 3600] m; the head floats
  `headGapFrac 0.35` × size above the stem top. `boundingSphere = null` on EVERY instance change.
- **HOVER-BOUNCE TRAP (fixed):** hover and pulse must NEVER multiply the size that derives the
  LAYOUT (stem height + head centre) — the head lifts out from under the cursor, hover drops, it
  falls back, and it oscillates. Layout always uses the BASE `headSizeM`; hover and pulse multiply
  only the head/flare instance scale, so they grow IN PLACE. Hover also brightens and solidifies via
  a per-instance `aHover` attribute (head geometry only); the rest state is deliberately airier.

## PRECISION TRAP (owner-reported "flickery/patchy" heads at close zoom) — ROOT CAUSE + FIX
ECEF ~6.4e6 m: viewMatrix(f32) × instanceTranslation(f32) on the GPU = large×large
cancellation → ~0.5 m quantisation that CRAWLS with camera motion (the PhotoFrustum lesson,
instanced edition). FIX (structural):
1. Every matrix rebuild sets `mesh.position = camera.position` on all three meshes and
   composes instance translations CAMERA-RELATIVE (`p − camera.position`).
2. Shaders use ONLY `projectionMatrix * modelViewMatrix * instanceMatrix` — the f64
   large-cancellation happens CPU-side in three's MV product. Fresnel in VIEW space
   (`V = normalize(-mvPos)`), flare billboards offset along view axes.
3. `hoverAnchor()` must ADD `heads.position` back (instance matrices are relative now).
Raycasting is unaffected (three composes matrixWorld × instanceMatrix). Verified: consecutive
close-zoom frames pixel-stable.

- `clusterLayout(pins)`: same-gh6 pins get evenly spaced stem-height slots (ranked by `hash01(id)`)

- **ADAPTIVE DE-CLUSTER (final; supersedes both the anchor-scatter AND the head-lean — owner:

  coords); only the per-frame DISPLAYED copies move. Behaviour by camera→cluster distance:
  · FAR (≥ PINS.clusterSingleDistM 300 km): ONE marker per cluster (rank-0 rep; others
    scale 0 = unpickable). Hover → "N PHOTOS HERE · CLICK TO ZOOM IN" (store `hoverCount`,
    card variant). Click → requestFly to clusterDiveAltM 60 km, NEVER opens a pin.

  · NEAR (≤ clusterMergeDistM 1 km, ramping from 2 km): the ring folds onto TRUE coordinates, and

  · SELECTED pin (`viewingPinId` → `pins.setSelected`) eases to its truth at any range

## Explore ambient journey (globe/explore.ts + EXPLORE tuning)
- Store seam `camera.exploreActive` / `setExplore`; nav `<a data-explore>` bound by
  `panels/ExploreMode.tsx` (entry only from idle/viewing states; unwinds FPV/temp-pin first).
- Controller states: dwelling (6 s + a slow 0.12°/s orbit about the pin axis, so the journey never
  freezes when all pins share one city) → cruising (constant-ω great-circle, ω =
  `clamp(arc/legTargetS, …)` with an edge ramp) → next pin. Order is a greedy
  `orderByNearestNeighbour` from the view focus; exhausted → re-order fresh.
- Look-ahead geometry (pure): γ = `asin((R+h)/R·sin α) − α` (≈10.9° at 900 km / 50°) — the camera
  rests γ BEHIND the pin and looks γ ahead along the travel tangent during a leg, so the look-at
  lands exactly on the pin at arrival. Rays past the limb clamp to `acos(R/(R+h))`.
- Exits never fight the user: `noteInteract` (canvas pointer/wheel/touch), Escape (TOP of the unwind
  chain), encoder/slider steering, search fly-to. reduceMotion turns legs into instant cuts.

### Welcome-start fix (owner follow-up — SUPERSEDES the entry flight above; browser-VERIFIED)
The welcome load must open ALREADY GLIDING, with no lunge at the first pin, and cruise 2× faster.
- The `"entering"` state is REMOVED. `setActive(true)` → `"arming"`; the first `update()` calls
  `begin(nowMs)` (it needs the frame clock), which NN-orders and `startLeg`s from the CURRENT camera
  pose. The <2-pins fallback no longer flies to the explore pose either — idle drift owns until the
  viewport query lands ≥2 pins. `poseFor`/flight remain ONLY for reduced-motion leg cuts.
- The entry pose is absorbed by the altitude low-pass plus a NEW `easeLookToward` view-ray low-pass
  (τ `poseEaseTauMs` 1200 ms, cap `lookMaxRateDegPerS` 12°/s), eased in **TILT/HEADING space at the
  camera**. TWO MEASURED TRAPS got it there:
  1. A pure exponential err/τ on a ~120° entry error is a **>90°/s whip pan** (110°/s measured).
  2. Easing the look POINT along the surface, even rate-capped, drags the gaze **through a nadir
     stare** mid-pan, because the surface great-circle between the two look points passes near the
     sub-camera point — and a geocentric look-point cap is amplified ~R/d (4–6×) into camera swing.
     Angle-space easing fixes both. `seedLook` reads the camera's ACTUAL forward ray, so the initial
     error is zero.
- Speed ×2: `legTargetS` 28→14, ω band 0.12–1.1°/s.
- Verified by scripted headless-Chrome CDP (`scripts/verify-explore-welcome.mjs`; Node ≥22 for a
  global WebSocket): no flight on welcome load, fallback (0.5 s) → cruising → dwelling, max
  camera-ray rate 10.6°/s, min tilt 49.9° (no nadir dip), alt 1100→900 km ease.
