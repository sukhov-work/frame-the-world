## THE HEADLINE: five checks that could not fail
Four of them written in the same session that "verified" the feature. This is the finding
class to carry forward — the gates looked green and were measuring nothing.
1. **C4 — structurally unfalsifiable.** A regex captured up to `visibility: hidden`, then the
   test asserted that capture did NOT contain `display: none`. It never could.
2. **C2 — the absolute that was already true.** "the scrubber is LIFTED clear of the bar"
   held with the lift **deleted**: the base `bottom: 2.2rem` (35.2 px) already exceeds the
   13.6 px bar. **RULE: a check on a lift/offset must measure the DELTA, never the absolute.**
3. **C1 — the counter that never counted.** The Esri GET counter only fires in satellite
   ground mode, and `/tmp/ftw-cdp` PERSISTS that pref across verify sessions. The settle check
   printed the count and never asserted `> 0` — so the whole leg could pass on zero traffic,
   and the reported "≈0 new GETs"/"~600 GETs/leg" would have been fiction.
   **RULE: a counter needs a positive control + its precondition pinned.**
4. **C3 — the no-op that looked like success.** ◉ had just centred the chart ON the eye, so a
   follow-up walk that moved nothing left distance ≈0 and "following RESUMED" passed.
   **RULE: every "it responded" check needs a trigger guard proving the stimulus happened.**
5. **C5 — the vacuous guard.** The viewport loop captured `altPresent` and never asserted it;
   `.m-altcol` mounts only in FPV, so a reordering would pass all three sizes vacuously — on
   the one occlusion the loop exists to disprove.
